# Cahier de Charge - Smart Door Access System

## 1. Executive Summary

A lightweight mobile application and web-based system that enables a homeowner (admin) to remotely control door access and manage guest face registration. The system allows the admin to unlock the door from their phone and grant time-limited access to guests via face recognition registration links.

---

## 2. Project Overview

### 2.1 Objective
Create a simple smart door access control system with two main features:
1. **Remote Door Control**: Admin can unlock the door remotely from their mobile app
2. **Guest Face Registration**: Admin can send one-time registration links to guests for face capture and storage

### 2.2 Scope
- **In Scope**:
  - Android mobile application (admin app)
  - Web-based guest registration interface (accessible via link)
  - Backend API (FastAPI)
  - Database (Supabase PostgreSQL)
  - Guest management (create, view, delete, disable)
  - Real-time notifications for door events

- **Out of Scope**:
  - Door hardware integration
  - Face recognition algorithm (handled by door hardware)
  - Live camera feed from door

## 3. Functional Requirements

### 3.1 Admin Mobile App (Android)

#### 3.1.1 Authentication & Session
- **Login**: Simple PIN or password-based authentication (one admin user)
- **Session Management**: Admin remains logged in persistently (no automatic logout)
- **Secure Storage**: Credentials stored securely on device

#### 3.1.2 Dashboard
- **Real-time Status**: Display current door lock status (locked/unlocked)
- **Quick Action Button**: Large button to unlock/lock door remotely
- **Active Guests List**: Display all registered guests and their status
- **Notifications Center**: Show recent door events (unlocked by admin, recognized guest, registration alerts)

#### 3.1.3 Door Control
- **Remote Unlock**: Send unlock command to backend
- **Door Duration**: Door remains unlocked for exactly **5 seconds** after unlock command
- **Confirmation**: Show visual/toast confirmation after unlock action
- **Error Handling**: Display error messages if unlock fails

#### 3.1.4 Guest Management
- **View Guests**: List all registered and pending guests
  - Display: Guest name, email, registration status, face registration date
- **Generate Invite Link**: 
  - Create one-time registration link
  - Link valid for **2 hours** only
  - Display link with copy button (or share via email if applicable)
  - Mark link as "sent" or "pending"
- **Delete Guest**: Permanently remove a guest from the system
- **Disable Guest**: Deactivate a guest without deletion (can be re-enabled)
- **Enable Guest**: Re-activate a previously disabled guest

#### 3.1.5 Notifications
- **Door Opened**: Notify when door is unlocked (admin action or guest face recognition)
- **Guest Registration**: Notify when a guest successfully registers their face
- **Failed Registration**: Notify if guest registration attempt fails

#### 3.1.6 UI/UX
- Clean, minimal interface
- Large buttons for accessibility
- Real-time status updates
- Offline capability: Show cached data if backend is unavailable

---

### 3.2 Guest Registration Web Interface

#### 3.2.1 Access
- **One-time Link**: Generated by admin, valid for **2 hours**
- **No Login Required**: Guest accesses directly via link
- **Responsive Design**: Mobile-friendly (accessed on guest's phone)

#### 3.2.2 Registration Flow
1. Guest opens invite link in browser
2. Display welcome message with homeowner's name
3. Request camera permission
4. **Face Capture**: 
   - Simple single-photo capture (no multiple angles or video required)
   - Instructions: "Take a clear photo of your face"
   - Camera feed preview
   - Capture button to take photo
   - Retake option if not satisfied
5. **Upload & Confirmation**:
   - Upload captured face image to Supabase storage
   - Save face metadata to database
   - Display success message
   - Provide app download link or close

#### 3.2.3 Validation
- Verify link is valid and not expired
- Prevent duplicate registrations on same link
- Validate face image quality (basic check: image not blank, reasonable size)
- Handle expired/invalid links gracefully

### 4.3 Database Schema

#### Users Table (Admin)
```sql
CREATE TABLE users (
  id SERIAL PRIMARY KEY,
  email VARCHAR(255) UNIQUE NOT NULL,
  password_hash VARCHAR(255) NOT NULL,
  name VARCHAR(255),
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

#### Guests Table
```sql
CREATE TABLE guests (
  id SERIAL PRIMARY KEY,
  admin_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  name VARCHAR(255) NOT NULL,
  email VARCHAR(255),
  status ENUM('pending', 'registered', 'disabled') DEFAULT 'pending',
  face_image_url VARCHAR(500),
  face_registration_date TIMESTAMP,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);
```

#### Registration Links Table
```sql
CREATE TABLE registration_links (
  id SERIAL PRIMARY KEY,
  guest_id INTEGER NOT NULL REFERENCES guests(id) ON DELETE CASCADE,
  token VARCHAR(255) UNIQUE NOT NULL,
  expires_at TIMESTAMP NOT NULL,
  used_at TIMESTAMP,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

#### Notifications Table
```sql
CREATE TABLE notifications (
  id SERIAL PRIMARY KEY,
  admin_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  type ENUM('door_opened', 'guest_registered', 'registration_failed') NOT NULL,
  message TEXT NOT NULL,
  guest_id INTEGER REFERENCES guests(id) ON DELETE SET NULL,
  read BOOLEAN DEFAULT FALSE,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

## 5. API Endpoints (FastAPI)

### 5.1 Authentication
| Method | Endpoint | Description |
|--------|----------|-------------|
| POST | `/api/auth/login` | Admin login with email/password |
| POST | `/api/auth/logout` | Admin logout |
| GET | `/api/auth/me` | Get current admin info |

### 5.2 Door Control
| Method | Endpoint | Description |
|--------|----------|-------------|
| POST | `/api/door/unlock` | Send unlock command |
| GET | `/api/door/status` | Get current door status |

### 5.3 Guest Management
| Method | Endpoint | Description |
|--------|----------|-------------|
| GET | `/api/guests` | List all guests |
| POST | `/api/guests` | Create new guest |
| GET | `/api/guests/{guest_id}` | Get guest details |
| PATCH | `/api/guests/{guest_id}` | Update guest (disable/enable) |
| DELETE | `/api/guests/{guest_id}` | Delete guest |

### 5.4 Registration Links
| Method | Endpoint | Description |
|--------|----------|-------------|
| POST | `/api/registration/generate-link` | Generate one-time registration link |
| GET | `/api/registration/link/{token}` | Validate and retrieve link info |
| POST | `/api/registration/upload-face` | Upload face image (guest) |

### 5.5 Notifications
| Method | Endpoint | Description |
|--------|----------|-------------|
| GET | `/api/notifications` | Get all notifications |
| PATCH | `/api/notifications/{notification_id}` | Mark as read |

## 6. Non-Functional Requirements

### 6.1 Security
- **Authentication**: JWT tokens with 24-hour expiration
- **HTTPS**: All communication encrypted
- **Password**: Admin password minimum 8 characters, hashed with bcrypt
- **Face Images**: Stored securely in Supabase Storage with restricted access
- **Rate Limiting**: Prevent brute-force attacks on login
- **CORS**: Properly configured for web registration interface

### 6.2 Performance
- **API Response Time**: < 2 seconds for most endpoints
- **Mobile App**: < 100 MB APK size
- **Database Queries**: Optimized with indexes

### 6.3 Reliability
- **Uptime**: 99% availability target
- **Error Handling**: Graceful degradation if backend unavailable
- **Offline Mode**: App caches door status and guest list

### 6.4 Scalability
- **Single Admin User**: App designed for single user, but architecture supports future multi-admin
- **Guest Limit**: No hard limit (Supabase can handle thousands of guests)

### 6.5 Usability
- **Accessibility**: Large buttons, high contrast
- **Responsiveness**: Works on Android 8.0+
- **Simple UI**: Minimize complexity, maximize clarity

## 9. Constraints & Assumptions

### 9.1 Constraints
- Single admin user only
- Door hardware integration is out of scope (face recognition happens on hardware)
- No live camera feed from door
- No audit logging required
- Minimal fancy UI/animations

### 9.2 Assumptions
- Admin has reliable internet connection
- Door hardware has built-in face recognition capability
- Guests have smartphones to access registration link
- Backend server is always available (simple setup, no redundancy)

## 10. Risks & Mitigation

| Risk | Impact | Mitigation |
|------|--------|-----------|
| **Guest face image quality** | Face recognition fails | Add basic validation, provide clear capture instructions |
| **Network latency** | Slow unlock response | Implement timeout handling, show loading state |
| **Supabase downtime** | App becomes unusable | Implement local caching, offline detection |
| **Link expiration confusion** | Guest can't register | Display clear expiration time in UI |
| **Face privacy** | Security concern | Encrypt face images, restrict access, clear GDPR compliance |
